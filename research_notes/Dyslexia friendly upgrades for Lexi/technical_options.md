Research date: 2026-10-17. Method note: besides web pages, several facts were pulled directly from primary machine endpoints (npm registry JSON, Hugging Face model API, Google Fonts CSS API, jsDelivr data API, caniuse). Those URLs are cited inline. Where a figure came from an AI-summarised page fetch rather than raw text, it is flagged. ## 1. Word-level highlighting synced to TTS

### Takeaway
Word highlighting is feasible everywhere but via three different mechanisms: (a) live `boundary` events from system TTS (web `onboundary`, expo-speech `onBoundary`) which are reliable only with local/native voices and are patchy on Android Chrome and online voices; (b) precomputed word timings for pre-recorded Piper clips (Piper's own code can emit per-phoneme sample counts if the ONNX model has the alignment output); (c) timestamps returned by cloud TTS (ElevenLabs/Azure) or by sherpa-onnx's alignment modes. Always feature-detect and keep a timer-estimate fallback.

### Cited Findings

**Web Speech API `boundary` event**
- MDN: `boundary` "fires when the spoken utterance reaches a word or sentence boundary"; it is a `SpeechSynthesisEvent`; the page is flagged "Limited availability" (not Baseline). The MDN page fetched did not itself list `charIndex`/`charLength` or voice caveats. — [MDN boundary event](https://developer.mozilla.org/en-US/docs/Web/API/SpeechSynthesisUtterance/boundary_event)
- caniuse/MDN-BCD data (fetched 2026-10-17): Chrome "partial support" from v33 through 157; Edge supported 14-154; Firefox supported 49-161; Safari supported 7-27.1; Safari iOS 7-27.2; Chrome Android "partial" (only v154 row listed); Firefox Android supported (v157 row listed). The "partial" flag on Chrome is consistent with the remote-voice issue below but the dataset does not say why. — [caniuse boundary event](https://caniuse.com/mdn-api_speechsynthesisutterance_boundary_event)
- Per-browser quirks (article dated 2020-11-23, so may be stale): `charIndex` is provided in all browsers, `charLength` in all except Safari; on Android Chrome and Firefox "the 'boundary' event does not fire"; macOS never reports `name: 'sentence'`; Chrome/Edge on Windows report sentence boundaries with `charLength` 0; for non-local voices Chrome will not speak if rate > 2; Safari `end` does not fire on `cancel()`; iOS speech is inaudible when the silent switch is on; voices load asynchronously (`onvoiceschanged`; Safari lacks `addEventListener` on `speechSynthesis`). — [Coder's Block, "JavaScript text to speech and its many quirks"](https://codersblock.com/blog/javascript-text-to-speech-and-its-many-quirks/)
- W3C public-speech-api list, 2021-06-28 (single developer report, untested on other browsers): "boundary events trigger only while using native voices" and "the boundary event does not work in chrome for android". — [W3C list post](https://lists.w3.org/Archives/Public/public-speech-api/2021Jun/0000.html). A 2015 W3C thread (surfaced via search, not fetched in full) reported `onboundary` not working for Chrome's remote voices. — [W3C list 2015Oct](https://lists.w3.org/Archives/Public/public-speech-api/2015Oct/0002.html). A 2017 Stack Overflow question (Chinese mirror, seen only via search snippet) links a Chromium bug and suggests it is a known, unlikely-to-be-fixed issue. — [mirror](https://cloud.tencent.cn/developer/ask/sof/114758503)
- Edge: the 2016 Edge speech launch post said `boundary` was not supported yet (listed as under evaluation); I found no authoritative current statement on whether Edge's "Online (Natural)" voices fire `boundary`. — [Windows blog 2016](https://blogs.windows.com/msedgedev/2016/06/01/introducing-speech-synthesis-api/)
- Edge/Chrome engineers on the W3C list agreed in 2016 to add a word-length value (later `charLength`) because it makes highlighting simpler. — [W3C 2016Nov/0000](https://lists.w3.org/Archives/Public/public-speech-api/2016Nov/0000.html), [reply](https://lists.w3.org/Archives/Public/public-speech-api/2016Nov/0001.html)

**CSS Custom Highlight API (for rendering the highlight without wrapping words in spans)**
- Support: Chrome 105, Edge 105, Firefox 140, Safari 17.2, Safari iOS 17.2 (Chrome Android row shows 154). — [caniuse Highlight API](https://caniuse.com/mdn-api_highlight)

**expo-speech (SDK 58; package `expo-speech@58.0.3`, MIT)**
- Docs: `onBoundary` is "invoked when the spoken utterance reaches a word"; `SpeechOptions` header says Android, iOS, Web; **no platform-specific note on onBoundary**; `onMark/onPause/onResume` are typed but undocumented; `onError` is Android/iOS; `pause()`/`resume()` iOS and Web only (not Android); `VoiceQuality` is only `Default` | `Enhanced` (no "Premium"); iOS physical devices are silent in silent mode; `maxSpeechInputLength` is platform-dependent. — [Expo Speech docs](https://docs.expo.dev/versions/latest/sdk/speech/); version/license — [npm registry](https://registry.npmjs.org/expo-speech/latest)
- Source (main branch): JS maps native event `Exponent.speakingWillSayNextString` to `onBoundary({charIndex, charLength})`, with no `Platform.OS` guard. — [Speech.ts](https://raw.githubusercontent.com/expo/expo/main/packages/expo-speech/src/Speech.ts)
- Android native: `UtteranceProgressListener.onRangeStart(utteranceId, start, end, frame)` is forwarded with `charIndex = start`, `charLength = end - start`; no API-level guard in the module. — [SpeechModule.kt](https://raw.githubusercontent.com/expo/expo/main/packages/expo-speech/android/src/main/java/expo/modules/speech/SpeechModule.kt)
- iOS native: `willSpeak(characterRange:utterance:)` emits `Exponent.speakingWillSayNextString` with `charIndex: characterRange.location` (fetched snippet showed charIndex; charLength not visible in the excerpt). — [SpeechModule.swift](https://raw.githubusercontent.com/expo/expo/main/packages/expo-speech/ios/SpeechModule.swift)
- Community: an Expo forum thread titled "expo-speech onBoundary text-to-speech callbacks do nothing" (March 2023) exists; only the title was visible. — [Expo forums tag](https://forums.expo.dev/tag/Speech)

**Word timestamps from Piper (for pre-recorded clips)**
- Rhasspy/piper (MIT) was archived 2025-10-06; "Development has moved" to OHF-Voice/piper1-gpl. — [rhasspy/piper](https://github.com/rhasspy/piper)
- piper1-gpl is GPL-3.0, `pip install piper-tts`, embeds espeak-ng for phonemization, offers Python/C/C++ APIs; seeking maintainers (96 open issues). — [OHF-Voice/piper1-gpl](https://github.com/OHF-Voice/piper1-gpl)
- piper1-gpl source exposes alignment: `AudioChunk.phoneme_id_samples` ("Number of audio samples for each phoneme id (alignments)") and `AudioChunk.phoneme_alignments` (list of `PhonemeAlignment{phoneme, phoneme_ids, num_samples}`); computed as `result[1] * config.hop_length` from the ONNX model's second output; if the model has only one output the code says "Alignment is not available from voice model"; `synthesize_wav(include_alignments=True)` returns them; `Voice.load` can patch a model via `add_alignment_output`. Alignment build can fail with a "Phoneme alignment failed" log if phoneme-id bookkeeping mismatches. — [voice.py](https://raw.githubusercontent.com/OHF-Voice/piper1-gpl/main/src/piper/voice.py)
- The documented Python API page does not mention alignments (SynthesisConfig shows `volume`, `length_scale`, `noise_scale`, `noise_w_scale`, `normalize_audio`). — [API_PYTHON.md](https://raw.githubusercontent.com/OHF-Voice/piper1-gpl/main/docs/API_PYTHON.md)
- Third-party corroboration of the same trick: floravox-cli ships `python/add_durations_output.py` which patches a VITS/Piper ONNX model to expose per-phoneme durations; `sum(durations) x hop_length == audio samples`; unpatched models fall back to proportional estimates flagged `estimated: true`. Floravox code is Apache-2.0 OR MIT. — [floravox-cli docs.rs](https://docs.rs/crate/floravox-cli/0.8.1)

**Word timestamps from other neural/cloud TTS**
- kokoro-js: streaming chunks yield `text`, `phonemes`, `audio`; README does not mention timestamps. — [kokoro.js README](https://github.com/hexgrad/kokoro/tree/main/kokoro.js). The Python Kokoro README snippet also shows only `(graphemes, phonemes, audio)`. — [hexgrad/kokoro](https://github.com/hexgrad/kokoro)
- Kokoro ports (ExecuTorch, Core ML) return one duration per phoneme; Core ML notes say decoder frames are 600 samples at 24 kHz (25 ms/frame); a Replicate wrapper advertises English word-level timestamps. (Third-party model cards/aggregators; grouping phonemes into words is the app's job.) — [Kokoro Core ML card](https://huggingface.co/toddkrabach/Kokoro-82M-CoreML), [ExecuTorch card](https://huggingface.co/mlboydaisuke/Kokoro-82M-ExecuTorch), [Replicate](https://replicate.com/siegerts/kokoro-tts-82m)
- react-native-sherpa-onnx: TTS alignment at sentence/word/character granularity, "fast estimated mode or accurate wav2vec2 CTC forced-alignment mode"; no per-phoneme timestamps mentioned. — [XDcobra/react-native-sherpa-onnx](https://github.com/XDcobra/react-native-sherpa-onnx)
- ElevenLabs `POST /v1/text-to-speech/{voice_id}/with-timestamps` returns `audio_base64` plus `alignment` and `normalized_alignment` (parallel arrays `characters`, `character_start_times_seconds`, `character_end_times_seconds`) — character-level, so words must be rebuilt by the client. — [ElevenLabs API ref](https://elevenlabs.io/docs/api-reference/text-to-speech/convert-with-timestamps)
- Azure Speech SDK `WordBoundary` event: raised at the beginning of each word/punctuation/sentence with time offset in ticks and character position; JS example sets `SpeechServiceResponse_RequestSentenceBoundary`; events arrive faster than playback so the caller must synchronize. Docs do not state browser support for the events explicitly. — [Azure how-to-speech-synthesis](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/how-to-speech-synthesis)
- Third-party clients that reproduce Edge "Read Aloud" (kothok-edge-tts, react-native-edge-tts) return word-boundary timings but are unofficial. — [docs.rs kothok-edge-tts](https://docs.rs/kothok-edge-tts), [react-native-edge-tts README](https://cdn.jsdelivr.net/npm/react-native-edge-tts@2.0.0/README.md)

### Inferences
- Because Lexi already ships pre-recorded Piper clips, the cheapest robust path is **offline, build-time alignment**: run piper1-gpl (or a patched model) with `include_alignments=True` over every canned phrase, group phoneme alignments into words (espeak phoneme output separates words with spaces, so splitting the phoneme list on space tokens should map to words; this mapping is my inference and must be validated), and ship a `{wordStart, wordEnd, tMs}` JSON beside each clip. Highlight in-app from `expo-audio` playback position (web: `audio.currentTime` via `requestAnimationFrame`). This works identically on web and native and needs no runtime `boundary` support. A forced aligner (e.g. wav2vec2 CTC, as sherpa-onnx RN uses) is the fallback if alignments cannot be extracted from a given voice.
- For dynamic text via system TTS: use `boundary`/`onBoundary` when events are observed within ~1 s of start; otherwise fall back to a timer that distributes words across estimated duration (the web search found this suggested but no source confirming it on current Chrome Android). Detect at runtime, per voice, rather than by UA sniffing. Prefer `localService === true` voices on web when highlighting matters.
- Because the web build uses `speechSynthesis`, treat Chrome desktop "Google ..." network voices and Android Chrome as "may not emit boundary" until tested; Safari and Firefox desktop with local voices are the most likely to work. Safari lacks `charLength`, so derive word end by scanning to the next whitespace from `charIndex`.
- CSS Custom Highlight API (`CSS.highlights`) is widely available enough (Chrome/Edge 105, Safari 17.2, Firefox 140) to highlight a word range without mutating the DOM, with a span-wrapping fallback for older browsers.
- On native, `onBoundary` is wired for both OSes in source, so it is probably functional with system voices, but the docs make no platform guarantee; real behaviour depends on the Android TTS engine implementing `onRangeStart` (Google TTS vs Samsung vs others).

### Gaps
- No authoritative, current (2025-2026) test matrix for `boundary` with Chrome desktop network voices or Edge "Online (Natural)" voices; the evidence is 2015-2021 mailing-list posts. The Chromium bug itself was not located.
- Could not confirm Android API level or engine requirements for `onRangeStart` (module code has no guard; Android reference not fetched) or which Android TTS engines actually emit it.
- Did not verify that `charLength` is sent by the iOS native module (TS type says it is).
- Could not confirm which stock Piper voices ship with the alignment (second) output vs need patching; `rhasspy/piper-voices` model cards not inspected.
- Google Cloud TTS timepoints (SSML `<mark>`) not researched. expo-audio playback-position update frequency not verified (relevant to highlight smoothness).
- Kokoro Python word-timestamp behaviour (token start/end times) not confirmed from the README.

## 2. Natural TTS for dynamic text (on-device browser, on-device RN, cloud, iOS Personal Voice/premium)

### Takeaway
For the web artifact, runtime-downloaded neural TTS and cloud TTS are almost certainly unworkable (CSP blocks model/API fetches; model weights of 86-325 MB exceed the 16 MB page budget), so the realistic web options are system `speechSynthesis` for dynamic text plus bundled pre-recorded clips for canned phrases. On native, react-native-sherpa-onnx (MIT, Piper/Kokoro/Matcha on-device, streaming, alignments) is the most capable on-device route, with expo-speech Enhanced voices as the zero-cost baseline; cloud TTS is cheap but sends journal text to another third party.

### Inferences
- **Web artifact:** neither `kokoro-js` nor `piper-tts-web` can be recommended. They fetch model files (86-325 MB for Kokoro; ~63-114 MB for Piper) and WASM at runtime from huggingface.co/CDNs, which the stated CSP blocks, and bundling is impractical against a 16 MB page limit (and the artifact asset types are "standard web media types only", which likely excludes `.onnx`). ONNX Runtime Web multithreading also normally needs cross-origin isolation, which a sandboxed artifact iframe likely cannot provide (not verified). Realistic web plan: (1) pre-rendered Piper clips for the fixed phrases (already done), (2) `speechSynthesis` with the best local voice for dynamic text, preferring "Enhanced/Natural/Premium" local voices, (3) optional graceful degradation messaging when only a robotic voice exists.
- **Native:** sherpa-onnx RN is the strongest path to "natural voices for dynamic text" offline. A Piper medium voice is 63 MB (or Kokoro q8/q8f16 86-92 MB) which is a significant but tolerable download; ship on first run via the library's download manager rather than in the binary. Requires a dev build (native module), which Lexi already needs for expo-speech-recognition and expo-sqlite is bundled in Expo anyway. It also gives word/char alignments for highlighting (section 1). Licence checks needed: sherpa-onnx RN is MIT + LGPL parts; Piper voices are per-voice licensed (some restrictive) and the GPL espeak-ng phonemizer is embedded in Piper-family pipelines (sherpa-onnx ships espeak-ng data); Kokoro is Apache-2.0 and has the cleanest licence story.
- **Cloud TTS** is cheap for short phrases (e.g. at $15/1M chars, 100 characters per reply costs ~$0.0015) but it sends journal-derived text to a second third-party, adds an API key/proxy requirement and is blocked on the web artifact; the app already sends text to Anthropic with the user's key, but adding another vendor widens the privacy surface for a vulnerable audience. Zero-retention modes appear enterprise-only for ElevenLabs.
- **Personal Voice** is relevant only as an optional "read my journal back in my own voice" feature on iOS; it needs a native authorization call that expo-speech does not provide (a small Expo module or a library would be required), is gated by user settings, and Apple frames it for AAC use. Treat as low priority / stretch.
- Expect `Enhanced` iOS voices (downloaded by the user in Settings > Accessibility > Spoken Content) to be materially better than `Default`; the app can list them with `getAvailableVoicesAsync()` and nudge the user to download one.

### Gaps
- No measured latency/real-time-factor for Kokoro or Piper on mid-range phones (WASM or native) found; sherpa-onnx RN README gave no benchmarks.
- Apple's `AVSpeechSynthesisVoiceQuality.premium` (iOS 16+) and whether expo-speech surfaces it were not verified (Expo enum has only Default/Enhanced).
- Info.plist usage-description key required for Personal Voice not confirmed.
- Azure and Google per-character prices not retrieved; Kokoro per-voice quality grades in the README not extracted. Provenance of the unscoped `piper-tts-web` package unverified.
- Whether the web artifact sandbox allows same-origin fetches of multi-file bundled binaries (e.g. chunked model files) is unknown and would need an empirical test; likewise whether jsDelivr-hosted WASM can be fetched by the ONNX runtime under that CSP.
- sherpa-onnx RN compatibility with RN 0.88 / SDK 58 (README says RN 0.70+) not tested.

## 3. Speech-to-text (expo-speech-recognition, Whisper on device, browser Web Speech)

### Takeaway
`expo-speech-recognition@58.0.0` (MIT, published 2026-10-16, tracks the Expo SDK) already covers on-device mode, punctuation and contextual biasing through the OS recognisers. whisper.rn (MIT) is the on-device Whisper/Parakeet option but needs a prebuild and 32-488 MB models; no dyslexia-specific accuracy data exist. Browser recognition is server-based in Chrome (audio leaves the device), Chrome 139+ can opt into on-device packs, and the artifact has no microphone anyway.

### Cited Findings

**expo-speech-recognition**
- `expo-speech-recognition@58.0.0`, MIT, published 2026-10-16T01:50Z (one day before this research; track for early-release bugs). — [npm registry](https://registry.npmjs.org/expo-speech-recognition/latest), [publish time](https://registry.npmjs.org/expo-speech-recognition)

**Accuracy on atypical speech**
- ICLR 2025 evaluation on children with speech impairments (dysarthria, stuttering, cerebral palsy): all models made substantial errors; Whisper had moderate success but often treated disordered speech as noise. — [ICLR 2025 listing](https://www.iclr.cc/virtual/2025/34325)
- Dutch MA thesis: fine-tuning Whisper gave limited WER reduction for moderate/severe dysarthria and made mild cases worse; Whisper did not beat a hybrid ASR model on any speaker. — [RUG thesis](https://campus-fryslan.studenttheses.ub.rug.nl/377/1/MA%204957180%20L%20Feenstra.pdf)
- 2025 arXiv paper prompts Whisper for verbatim transcription / reading-miscue detection in children and in adults with Parkinson's, ALS, CP, Down syndrome (WER numbers not captured). — [arXiv 2505.23627](https://arxiv.org/pdf/2505.23627)
- Searches found no published Whisper WER for speakers with dyslexia; the only dyslexia-specific ASR item was a 2010 non-Whisper reading tutor paper. — [IATED 2010](https://library.iated.org/view/HUSNI2010MIN)

**Browser Web Speech recognition**
- MDN: "On some browsers, like Chrome, using Speech Recognition ... involves a server-based recognition engine. Your audio is sent to a web service ... so it won't work offline." Feature is "Limited availability". Has `processLocally`, static `available()` and `install()` for on-device language packs, `phrases` for contextual biasing, `lang`, `continuous`, `interimResults`; `grammars` is deprecated/no effect. — [MDN SpeechRecognition](https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognition)
- Chrome 139 (2025-08-05) added on-device recognition: `processLocally = true` forces local processing; requires a language pack, otherwise `start()` fails with a language-not-supported error; `available()` is governed by an `on-device-speech-recognition` Permissions-Policy; MDN marks `processLocally` experimental. Microsoft documents a similar local model in Edge (Edge 150 language list). — [Chrome 139 blog](https://developer.chrome.com/blog/new-in-chrome-139), [MDN processLocally](https://developer.mozilla.org/docs/Web/API/SpeechRecognition/processLocally), [Edge speech recognition API](https://learn.microsoft.com/fi-fi/microsoft-edge/web-platform/speech-recognition-api)
- Firefox has no `SpeechRecognition` implementation per the expo-speech-recognition README. — [GitHub README](https://github.com/jamsch/expo-speech-recognition)

### Inferences
- For native dictation, `requiresOnDeviceRecognition: true` + `addsPunctuation: true` + `contextualStrings` (seeded with the user's frequent words/names and emoji-labelled vocabulary) is the lowest-effort path and keeps audio off the network, but only where the OS offers it (Android 13+/iOS per README); fall back to server recognition with explicit consent otherwise.
- Whisper via whisper.rn is justified only if OS dictation proves unsatisfactory (e.g. weak on non-standard pronunciation, or Android <13). It would add a 32-190 MB model (tiny/base/small q5_1) and a second mic pipeline that can conflict with expo-speech-recognition's audio session. Quantized `base.en` q5_1 (60 MB) is the typical size/accuracy compromise (my judgement, not benchmarked).
- Dyslexia is primarily a reading/spelling difference; the literature found here shows ASR degradation for motor-speech and fluency disorders, not dyslexia, so there is no evidence here that dyslexic speakers need a different recogniser. Dictation output, however, will be spelled correctly by the recogniser, which can mask the user's own spelling practice, a product consideration rather than a technical one.
- The web artifact cannot use recognition (no mic), so web STT is out of scope regardless of Chrome 139 on-device mode.

### Gaps
- No quantitative accuracy figures for OS recognisers (SFSpeechRecognizer/Android) on dyslexic or otherwise atypical speech; none found for Whisper-specific dyslexia.
- Raw README table for expo-speech-recognition not read directly (iOS version requirement for on-device mode needs re-verification; Apple's `SFSpeechRecognizer.supportsOnDeviceRecognition` historically began earlier).
- Safari's `SpeechRecognition` status and caniuse data for it not retrieved.
- whisper.rn/Expo SDK 58 compatibility and real-world latency for tiny/base on mid-range phones not verified; whisper.cpp word-timestamp support in whisper.rn not documented.

## 4. OS accessibility settings (React Native/Expo and CSS media queries)

### Takeaway
RN exposes font scale, reduce motion and screen-reader state cross-platform, but bold text, increase contrast, invert/grayscale and "darker system colors" are platform-split and mostly iOS-only; contrast on Android is via `isHighTextContrastEnabled`. CSS `prefers-reduced-motion`, `prefers-contrast` and `forced-colors` are broadly supported in all current engines.

### Cited Findings

**React Native / Expo**
- `AccessibilityInfo`: `isScreenReaderEnabled()` (both; event `screenReaderChanged`); `isReduceMotionEnabled()` (both; event `reduceMotionChanged`; also true when Android "Transition animation scale" is off); `isAccessibilityServiceEnabled()` (Android; any service incl. third party); iOS-only: `isBoldTextEnabled()` (`boldTextChanged`), `isGrayscaleEnabled()`, `isInvertColorsEnabled()`, `isReduceTransparencyEnabled()`, `isDarkerSystemColorsEnabled()`, `prefersCrossFadeTransitions()`; Android-only: `isHighTextContrastEnabled()`, `getRecommendedTimeoutMillis(originalTimeout)` ("Time to take action"). Events listed in docs: `screenReaderChanged`, `reduceMotionChanged`, `accessibilityServiceChanged` (Android), `boldTextChanged`, `grayscaleChanged`, `invertColorsChanged`, `reduceTransparencyChanged` (iOS), `announcementFinished` (iOS). `setAccessibilityFocus` is deprecated in favour of `sendAccessibilityEvent(..., 'focus')`. — [RN AccessibilityInfo](https://reactnative.dev/docs/accessibilityinfo)
- `PixelRatio.getFontScale()`: Android reflects Settings > Display > Font size; iOS reflects Settings > Display & Brightness > Text Size (and Accessibility > Larger Text); falls back to pixel ratio if unset. — [RN PixelRatio](https://reactnative.dev/docs/pixelratio)
- `<Text>`: `allowFontScaling` default true; `maxFontSizeMultiplier` (undefined inherits; 0 = no max; >=1 caps); `adjustsFontSizeToFit` + `minimumFontScale`; iOS-only `dynamicTypeRamp` (caption2 ... largeTitle, default `body`). — [RN Text](https://reactnative.dev/docs/text)
- Expo fonts doc: in SDK 58, `fontVariationSettings` works on `<Text>`/`<TextInput>` (RN 0.88+, Android 8+) - relevant for adjustable letter-shape axes in variable fonts. — [Expo fonts](https://docs.expo.dev/develop/user-interface/fonts/)

**CSS media queries (caniuse/MDN-BCD, fetched 2026-10-17)**
- `prefers-reduced-motion`: Chrome 74, Edge 79, Firefox 63, Safari 10.1, Safari iOS 10.3 (Chrome Android shows only a v154 row). — [caniuse](https://caniuse.com/mdn-css_at-rules_media_prefers-reduced-motion)
- `prefers-contrast`: Chrome 96, Edge 96, Firefox 101, Safari 14.1, Safari iOS 14.5. — [caniuse](https://caniuse.com/mdn-css_at-rules_media_prefers-contrast)
- `forced-colors`: Chrome 89, Edge 79, Firefox 89, Safari 16.0, Safari iOS 16.0. — [caniuse](https://caniuse.com/mdn-css_at-rules_media_forced-colors)

### Inferences
- Recommended native wiring: on mount and on `AppState` 'active', read `getFontScale()` (or `useWindowDimensions().fontScale`), `isReduceMotionEnabled`, `isScreenReaderEnabled`, plus `isBoldTextEnabled`/`isDarkerSystemColorsEnabled` on iOS and `isHighTextContrastEnabled` on Android; subscribe only to the events that exist. The docs list no change events for `isHighTextContrastEnabled` or `isDarkerSystemColorsEnabled`, so re-poll on foreground rather than assuming live updates.
- Do not set `allowFontScaling={false}` anywhere (dyslexic and low-vision users rely on it); instead use `maxFontSizeMultiplier` (e.g. 1.6-2.0) on dense UI chrome such as chips and emoji pickers and let message text scale freely; test at 200%.
- Treat in-app settings (font, spacing, ruler) as user overrides layered above OS signals, with OS reduce-motion forcing animations (emoji bounce, typewriter) off by default. Both `prefers-reduced-motion` and RN `isReduceMotionEnabled` are the same intent signal across web and native.
- On web, `forced-colors: active` (Windows High Contrast) overrides author colours, so highlighted-word and focus rings should use system colour keywords (`Highlight`, `CanvasText`) or borders in that mode. The artifact sandbox should still receive these media queries from the parent OS (not verified).

### Gaps
- Android "Bold text" (Android 12+ `fontWeightAdjustment`) has no RN API in the docs; would need a native module. Android 14+ non-linear font scaling (up to 200%) interaction with RN `fontScale` was not researched.
- Whether `isReduceMotionEnabled` on iOS fires when only "Prefer Cross-Fade Transitions" is set was not verified.
- caniuse Chrome Android rows show only v154, so exact Android Chrome support versions for the three media queries are not stated by that dataset (desktop Chrome versions are the reliable data).

## 5. Fonts (OpenDyslexic, Lexend, Atkinson Hyperlegible Next, Expo bundling, Android system fonts)

### Takeaway
Lexend and Atkinson Hyperlegible Next are on Google Fonts and Fontsource under OFL-1.1, tiny (12-15 KB per Latin woff2 weight) and easy to use in both apps. OpenDyslexic is OFL-1.1 on npm/Fontsource but NOT on Google Fonts, is about 8x larger (~115-120 KB per weight woff2), and must be inlined (web) or bundled (Expo). Efficacy evidence for dyslexia-specific fonts is weak, so offer choice rather than a single "dyslexic" font.

### Cited Findings

### Inferences
- **Web artifact:** load Lexend and Atkinson Hyperlegible Next with a `<link>` to Google Fonts (the only external stylesheet host the artifact contract permits). For OpenDyslexic, inline a base64 woff2 `@font-face`: regular alone is ~115 KB raw (~154 KB base64, my calculation), regular+bold ~315 KB, comfortably under 16 MB. Pulling it from jsDelivr as a `@font-face` URL is likely blocked since only scripts from CDNs are allowed (not verified). Subset to Latin to keep size down; consider omitting italics.
- **Native:** bundle chosen weights via the `expo-font` config plugin (build-time, no flash of unstyled text) and use the SDK 58 multi-face syntax or per-weight files. Avoid relying on `fontWeight` synthesis with custom fonts: register explicit regular/bold faces. Because RN has no fallback stack, check glyph coverage (emoji render from the system emoji font regardless; accented Latin is included in latin-ext files only).
- Verdana is a Microsoft font: iOS ships it, but Android's system fonts (Roboto/Noto per Expo's doc) do not include it, so any "Verdana" setting must be implemented by bundling a different font; this supports bundling Lexend/Atkinson/OpenDyslexic instead of relying on system fonts (the Verdana-on-Android claim itself was not independently sourced; see Gaps).
- Offer 3-4 fonts (system default, Lexend, Atkinson Hyperlegible Next, OpenDyslexic) with live preview, plus independent controls for size, line height, letter spacing and word spacing, since font effect on dyslexic reading is individual. Lexend and Atkinson are lightweight enough to preload for all users.

### Gaps
- No peer-reviewed evidence retrieved on the effectiveness of OpenDyslexic, Lexend or Atkinson for dyslexic readers; only that OpenDyslexic's benefit is "questioned".
- Not independently confirmed from an authoritative source that Verdana is absent on Android (Expo's doc only states Roboto default); not confirmed whether Expo-managed fonts need extra steps for variable font Lexend on Android < 10.
- Official OpenDyslexic repo licence file not read directly (Wikipedia and Fontsource npm metadata used).
- Actual CSP `font-src`/`style-src` behaviour of the artifact sandbox was not tested.

## 6. Spell-check (client-side phonetic libraries vs LLM; suggestions with audio)

### Takeaway
Client-side options are mature but generic: nspell (Hunspell-compatible, MIT) + `dictionary-en`, typo-js, SymSpell ports (`symspell-ex`), and phonetic-key libraries (`double-metaphone`, `talisman`). Nothing off-the-shelf is dyslexia-aware, and published work says conventional checkers miss many dyslexic errors (esp. real-word errors), so a hybrid (fast local candidates plus LLM re-ranking in context) is the most promising design.

### Cited Findings
- Package data (npm registry): `nspell@2.1.5` MIT (last published 2021-01-17; ~42 KB unpacked); `dictionary-en@4.0.0` (MIT AND BSD; ~575 KB unpacked); `typo-js@1.4.0` BSD-3-Clause (~2 MB unpacked); `double-metaphone@2.0.1` MIT (~34 KB); `talisman@1.1.4` MIT (phonetic/string-distance toolkit, ~550 KB); `symspell-ex@1.1.10` MIT (~66 KB). — [nspell](https://registry.npmjs.org/nspell/latest), [dictionary-en](https://registry.npmjs.org/dictionary-en/latest), [typo-js](https://registry.npmjs.org/typo-js/latest), [double-metaphone](https://registry.npmjs.org/double-metaphone/latest), [talisman](https://registry.npmjs.org/talisman/latest), [symspell-ex](https://registry.npmjs.org/symspell-ex/latest)
- Real Check (Rello, Ballesteros, Bigham, 2015): real-word errors are 17-21% of errors by people with dyslexia; mainstream checkers (Word, LibreOffice, Pages) fail to detect them (Word caught 5.82%); their system reached 50.42% precision and 65.93% recall. — as reported in search summary, [A Spellchecker for Dyslexia](https://a11y-paradise.onrender.com/reviews/69c8429e23baf4291d929d6c) (secondary; primary paper not fetched)
- A Purdue dissertation found spell checkers identified the target word for 53% of misspellings, with efficiency rising as the phonetic error level rose; an ETSU study found spell checkers overall ineffective at placing the target word first for students with learning disabilities. — [Purdue](https://docs.lib.purdue.edu/dissertations/AAI9713567), [ETSU](https://dc.etsu.edu/etsu-works/19143) (abstract-level via search)
- Aspell implements both a phonetic and a Levenshtein edit distance (Interspeech 2007 paper by Sitbon et al., mentioned in search results). — [Interspeech 2007 PDF](https://www.isca-archive.org/interspeech_2007/sitbon07_interspeech.pdf)
- A US patent describes matching against known dyslexia-specific misspelling variants with an error-rate threshold (concept only). — [US7779354](https://patents.google.com/patent/US7779354)
- I found no published evaluation of Double Metaphone or SymSpell specifically on dyslexic spelling.

### Inferences
- Candidate pipeline (feasible on both web and native; both can reuse JS): (1) tokenise the user's message; (2) flag tokens unknown to nspell + a small user dictionary; (3) generate candidates by nspell suggestions union SymSpell (edit distance <= 2-3) union words sharing a Double Metaphone/other phonetic key (catches "fone"->"phone", "wen"->"when" better than pure edit distance); (4) rank by phonetic similarity first and frequency second; (5) optionally send the sentence plus candidate list to Claude to choose the contextually correct word and to catch real-word errors ("there/their", "bed/bad"). The local steps keep latency near zero and work offline; the LLM step handles the 17-21% real-word-error class that local dictionaries cannot see. The LLM call can be rate-limited to "on send" or "on tap" to save cost and keep privacy control.
- Package weight: nspell + `dictionary-en` is ~0.6 MB unpacked, fine for native; for the single-file web artifact it could be loaded from jsDelivr/unpkg as a script (the permitted route) only if the dictionary can be inlined or shipped as a script (dictionary files are normally fetched as `.aff/.dic`, which are fetches; may need a pre-bundled JS dictionary). A compact word list with SymSpell ("deletes" index) is simpler to inline.
- Showing suggestions with audio: render each suggestion as a large tappable chip (word + emoji/short definition when available) with a speaker button; speaking each candidate uses the same TTS path as other audio (`speechSynthesis` / `expo-speech`, or pre-generated clips for the top few thousand words to get natural voices and consistent timing). Because homophones ("their/there") sound identical, pair audio with a context sentence or emoji to disambiguate (design inference).
- Because nspell has not been published since 2021 (and Hunspell-based suggestion quality depends on the `.aff` REP/PHONE tables), plan to maintain a thin wrapper and keep the suggestion generator swappable.

### Gaps
- No benchmark of nspell vs SymSpell vs Double Metaphone on a dyslexic spelling corpus; no verified list of language-specific dyslexia error patterns (letter reversals, omissions, phonetic spellings) was retrieved beyond the abstract-level studies.
- Not verified whether `dictionary-en` includes Hunspell `PHONE` tables or how well nspell's suggestions handle phonetic spellings.
- Primary Real Check paper not fetched; numbers come via a secondary summary.
- Cost/latency of using Claude Haiku-class models for per-message spell correction not measured (see the Claude API docs for current prices).

## 7. Line focus / reading ruler and syllable splitting

### Takeaway
Reading rulers/line focus are well-established UX features in commercial tools but no authoritative CSS recipe or evidence base turned up; implement with a pointer/scroll-tracked mask on web and per-line layout rectangles on native. Hyphenation libraries (Hypher with pattern packs; `hyphen`; Hyphenopoly) return typographic hyphenation points, not guaranteed syllables, so use them for visual chunking with a caveat or pre-split with a pronunciation dictionary.

### Cited Findings
- Reading-ruler concept: a horizontal line/band follows the pointer, optionally dimming content outside the active line(s); Kami "Reading Assist" offers a ruler or screen mask that tracks the cursor with adjustable colour, opacity, height, width; Helperbird markets a dyslexia reading ruler. The dyslexia benefit is asserted by vendors, not shown by peer-reviewed evidence in the sources found. — [Kami Reading Assist](https://help.kamiapp.com/en/articles/14026008-reading-assist), [Helperbird ruler](https://helperbird.com/features/ruler), [Helperbird explainer](https://www.helperbird.com/explained/reading-rulers/), [Evince blueprint](https://blueprints.launchpad.net/ubuntu/+spec/evince-reading-ruler)
- CSS Custom Highlight API support (Chrome/Edge 105, Firefox 140, Safari/iOS 17.2) could drive "current line/word" styling without extra DOM. — [caniuse](https://caniuse.com/mdn-api_highlight)
- `hypher@0.2.5` (BSD-3-Clause, last published 2016-12-19): `hyphenate(word)` returns parts (e.g. `['hy','phen','ation']`); `hyphenateText()` inserts soft hyphens (default `minLength` 4); language patterns in separate packages (e.g. `hyphenation.en-us`); does not handle hyphenated compounds; README never claims syllabification; 581 stars, no maintenance statement. — [bramstein/hypher](https://github.com/bramstein/hypher), [npm](https://registry.npmjs.org/hypher/latest)
- `hyphen@1.14.1` (ISC; ~9.2 MB unpacked because it carries all language patterns) and `hyphenopoly@6.1.0` (MIT, ~3.2 MB unpacked). — [npm hyphen](https://registry.npmjs.org/hyphen/latest), [npm hyphenopoly](https://registry.npmjs.org/hyphenopoly/latest)

### Inferences
- **Web ruler:** overlay approach: a fixed full-viewport element with `mask-image: linear-gradient(...)` (transparent band at pointer Y, dim elsewhere) updated via `pointermove`/`touchmove` (and keyboard Up/Down for non-pointer users), or a translucent dimming strip with two divs; respect `prefers-reduced-motion` (no easing) and `forced-colors` (use system colours). For TTS-synced focus, drive the band from the current word's `getBoundingClientRect()` (or Range rects) so the ruler follows the spoken line.
- **Native ruler:** use `onTextLayout` line metrics (per-line `y/height`, not researched here) to place a translucent band over the active line and dim others with absolute-positioned overlays; scrolling/`FlatList` virtualization complicates absolute positioning, so keep the ruler per-message-bubble or as a movable overlay driven by touch (untested design).
- **Syllables:** English hyphenation points frequently differ from syllables (e.g. morphological breaks like "read-ing" vs phonetic breaks), so for reading support prefer a pronunciation-based syllabifier (CMU dictionary stress/syllable counts) or a one-time LLM/dictionary pre-split of the lexicon; use Hypher (small, BSD) only when approximate chunks are acceptable. For the single-file web artifact, Hypher + `hyphenation.en-us` patterns can be loaded as scripts from unpkg/jsDelivr; CSS `hyphens: auto` is a browser-native alternative for line-breaking but provides no control over visual syllable coloring.
- Syllable colouring/spacing should be user-toggleable and off by default for emoji-first content, since added visual markup can itself increase crowding for some readers (design judgement; no source).
